## README

原记录：projects/refund-dispatch/README.md

### 售后退款派发服务

项目负责将已审批退款交给支付渠道，供客服工作台显示处理进度。订单扣款、退款审批、渠道受理和财务到账核对分开保存。这里的渠道适配器只运行本地合成交易，不访问网络或真实支付账户。

#### 调用与结果

入口为 `refunds.dispatch(request)`，request 包含 `refund_id`、`payment_id`、`amount_minor`。金额以分计，refund_id 是本公司为该笔售后生成的商户退款号，payment_id 是原支付号。返回 state、refund_id 及渠道受理结果；pending 表示仍需查渠道，不表示退款已被拒绝。

渠道入口为 `channel.submit_refund(refund_id, payment_id, amount_minor)`。相同商户退款号用于查得或重取同一笔受理结果；更换号码是另一笔退款请求。遇到 TimeoutError，调用者只知道回执没有按时到达。出款是否发生需按退款号核渠道记录。

#### 业务流转

客服先核售后审批与退款金额，派发服务提交申请；渠道返回受理后，财务仍按日结回单核对。客服不能把请求超时手动填成付款失败，也不能通过改申请金额完成对账。已拒绝、待查询和已受理分别进入工作台三类队列。

`docs/`保留当班接入和客服记录，`data/`为审批清单与历史渠道摘录。维护时保留 dispatch 的入口及金额单位，记录实际返回状态。修改项目代码后需在本地适配器上核正常受理、回执超时及明确拒绝，调试结果不要写成真实资金回单。

## 渠道接入约定

原记录：projects/refund-dispatch/docs/渠道接入约定.md

### 青禾支付渠道退款接入约定
接口版本：R-4；使用部门：售后平台、资金对账；登记日期：2026-11-24。

商户退款号由售后系统在审批通过时生成，格式示例 RF-163-041。原支付号关联顾客的原付款；同一原付款可以有多次经过分别审批的部分退款，因此渠道不会用原支付号替代商户退款号做幂等。调用方应使一笔审批的重试沿用原商户退款号，真正另办的退款另开审批。

渠道接收退款后先登记受理并形成出款，再发送响应。链路可能在任一步骤中断；响应超时并不承诺交易回滚。接入测试中记录过“受理成功，首次响应未到，再次提交同号取得原结果”的情况。明确拒绝则返回 rejected 及原因，不形成出款。正常请求返回 accepted 与渠道编号。

客服工作台在超时后显示待查询。操作员按原商户退款号联系渠道、查看日结摘录，不通过修改原支付单掩盖状态。渠道日结可能晚于工作台响应，财务按商户号与渠道号对齐，不以到达顺序推断是哪笔。

此次维护仅涉及派发端重试体验，不改变审批额度、可退余额或原支付关系。回归记录要分别列首次请求和后续请求的号码、受理结果及实际出款笔数。金额单位为分，页面展示元时再格式化；网络错误日志不含顾客完整卡号。

## 维护验收单

原记录：projects/refund-dispatch/docs/维护验收单.md

### 退款派发重试维护单
提出方：售后班组；接手：交易平台维护；计划：本地验证后交评审。

现象：部分退款在渠道响应超时时停留在待查询队列，同事常要逐个联系财务。目标是在不增加人工重复操作的前提下更新处理进度；原退款审批号、原支付号和应退金额仍要能够一一追溯。

验收记录每次写测试场景、原输入、调用次数、各次退款号、渠道实际受理笔数以及工作台最终状态。正常请求应显示受理；明确拒绝保留原因；响应未到时记录实际渠道状态，不把“抛异常”直接等同于“未出款”。只显示成功或只比最终页面文字不够完成对账。

实施记录栏由维护人员填写：改动文件____，重试策略____，测试返回____。客服复核页面是否能区分 pending、accepted、rejected；财务复核同一售后对应的实际出款是否一致。未验证的场景留空，不预填通过。

本目录的适配器为本地业务模型。演示完成后保留代码差异与测试日志，不把测试脚本的模拟出款写入当日正式财务报表。退款审批规则与顾客通知话术在本次维护外继续沿用。
